# Removing a worktree deletes its ignored files

**Scope:** transferable
**Area:** `git worktree remove`; any one-shot database write whose before-image is saved under a gitignored folder (`tmp/`) inside a worker's worktree (`.claude/worktrees/<name>`).
**Status:** open (a process rule: copy evidence out before removal)

## The symptom

On 2026-10-06 two production writes to the demo account were applied from worker worktrees, each with a before-image saved as the backfill rules require:

- `tmp/netsuite-backfills/organization-structure-44f2cfcf-…-2026-10-05T23-43-42-654Z.json` (39.8 MB, the whole previous `config_data`);
- `tmp/unclassified/before-image/44f2cfcf-…/` (61 `functional_processes` rows, the config row, the audit artifact).

After their branches merged, `git worktree remove .claude/worktrees/<name>` ran without a complaint, and both files were gone. `git worktree remove` refuses on untracked or modified files, so a clean removal reads as "nothing here but the branch".

## Why it was misleading

`git worktree remove` protects work: it refuses while the checkout has untracked or modified files, so a removal that succeeds looks like proof that nothing unique lived there. But ignored files don't count as untracked. Git deletes them with the directory and says nothing. The evidence a backfill keeps is deliberately ignored (it holds customer data and must never be committed), so it is exactly the class of file the safety check skips.

## Why it happens

Git only refuses for files it tracks or would show in `git status`. Ignored paths are outside both, so `remove` treats them as disposable build output.

## What to do

- Before removing a worktree that ran a write, copy its `tmp/` evidence (before-images, dry-run output, measurement scripts) into the main checkout's ignored `tmp/` first. Or have the worker write evidence there to begin with. Then remove.
- Check with `git -C <worktree> status --ignored --short` before `remove`. It lists what will vanish.
- If it is already lost, rebuild what you can from the write's own shape. The organization-structure catch-up only added `config_data.organizationStructureV1`, so the current row minus that key is the exact before-state; it was rebuilt to `tmp/netsuite-backfills/organization-structure-44f2cfcf-…-before-image-REBUILT-2026-10-06.json`. The functional reclassification is deterministic (re-running the classifier reproduced the stored rows 3,561/3,561), so the earlier rows can be regenerated by running the pre-change classifier at `a9da95eed` over the same version.
